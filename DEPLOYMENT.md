# Deploying the Email Job Scheduler (free tier)

This puts the whole app online so anyone can sign in with their own Google account, without your laptop running.

| Part | Where | Cost |
| --- | --- | --- |
| Frontend (React) | Vercel | free |
| Backend (API **and** worker, one process) | Render web service | free |
| Redis (BullMQ queue + rate-limit counters) | Render Key Value | free |
| Postgres | Neon | free |
| Search | Postgres fallback (Elasticsearch optional) | free |

**Why not run the backend on Vercel too?** Vercel runs short-lived serverless functions. This backend needs a process that stays alive: the BullMQ worker waits on Redis for delayed jobs and sends each email at its time. A serverless function can't wait an hour to send a scheduled email.

**Why the worker runs inside the API.** Render's free plan has no background workers, so `RUN_WORKER_IN_API=true` starts the worker in the same process as the API. Every guarantee still holds: the atomic claim, `jobId = email id`, and the Lua rate limiter are all enforced in Postgres and Redis, not in the process. Locally you can still run them as separate processes.

**Why there's no Elasticsearch.** There's no free hosted Elasticsearch. When `ELASTICSEARCH_URL` is empty, search queries Postgres instead: every word must appear in the subject, recipient or body, with the same highlighted results. That's case-insensitive substring matching, with no typo tolerance. If you set the variable to an Elastic Cloud or Bonsai URL, full search comes back automatically.

---

## 1. Neon: get the connection string

1. Neon console → your project → **Connect**.
2. **Turn off "Connection pooling"** and copy the URL. Its host must *not* contain `-pooler`.
   The migration runner uses a Postgres advisory lock, and that doesn't work through Neon's pooler (PgBouncer in transaction mode).
3. It looks like `postgresql://USER:PASSWORD@ep-xxxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.

## 2. Create the schema and sender accounts in Neon (once, from your laptop)

Senders are shared by all users, so this only needs to run once. In PowerShell:

```powershell
cd backend
$env:DATABASE_URL = "<your Neon URL from step 1>"
npm run migrate
npm run seed:senders
Remove-Item Env:DATABASE_URL
```

This uses the other values from your local `backend/.env`. The variable set in the shell overrides the file's `DATABASE_URL`.

## 3. Render: deploy the backend

1. Push this repo to GitHub.
2. [dashboard.render.com](https://dashboard.render.com) → **New** → **Blueprint** → pick the repo. Render reads [`render.yaml`](render.yaml) and creates the `email-scheduler-api` web service and the `email-scheduler-redis` Key Value instance.
   - Both use the `singapore` region. If your Neon database is elsewhere (e.g. `us-east`), change `region` in `render.yaml` for both services so database queries stay fast.
3. Render asks for the secret values:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | the Neon URL from step 1 |
| `FRONTEND_URL` | your Vercel URL, e.g. `https://reachinbox-scheduler.vercel.app` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | same as in your local `.env` |
| `GOOGLE_CALLBACK_URL` | `https://email-scheduler-api.onrender.com/api/auth/google/callback` |
| `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET` | same as in your local `.env` |
| `SLACK_REDIRECT_URI` | `https://email-scheduler-api.onrender.com/api/integrations/slack/callback` |
| `ELASTICSEARCH_URL` | leave empty |

`JWT_SECRET` and `BULL_BOARD_PASSWORD` are generated by Render. To log in to Bull Board, open the service → **Environment** to see the password.

4. Wait for the deploy, then open `https://email-scheduler-api.onrender.com/api/health`. You should see `"status": "ok"`.

> If Render gives the service a different URL (e.g. `email-scheduler-api-ab12.onrender.com`), use that URL everywhere below, and update `GOOGLE_CALLBACK_URL` and `SLACK_REDIRECT_URI` under **Environment**.

## 4. Google Cloud: allow the new callback, and let anyone sign in

In [Google Cloud console](https://console.cloud.google.com) → **Google Auth Platform**:

1. **Clients** → your Web client → **Authorized redirect URIs** → add
   `https://email-scheduler-api.onrender.com/api/auth/google/callback` → Save. Keep the localhost one for local development.
2. **Audience** → **Publish app** (status changes from *Testing* to *In production*).
   **This is what lets other people sign in.** In *Testing*, only the accounts listed as test users can log in; everyone else gets "Access blocked".
   The app only asks for `openid`, `email` and `profile`, which Google treats as non-sensitive, so publishing doesn't need a verification review.
3. **Branding**: set the home page to your Vercel URL and the privacy policy to `https://<your-vercel-app>/privacy.html`.

Changes can take a few minutes to apply.

## 5. Slack app: allow the new redirect

[api.slack.com/apps](https://api.slack.com/apps) → your app:

1. **OAuth & Permissions** → **Redirect URLs** → add
   `https://email-scheduler-api.onrender.com/api/integrations/slack/callback` → Save URLs.
2. To let visitors connect **their own** Slack workspaces: **Manage Distribution** → **Activate Public Distribution**. Without it, Slack only allows installs into your own workspace.

ngrok is no longer needed: Render already serves HTTPS.

## 6. Vercel: point the frontend at the backend

Vercel → your project → **Settings** → **Environment Variables**:

| Name | Value |
| --- | --- |
| `VITE_API_URL` | `https://email-scheduler-api.onrender.com` (no trailing slash) |

Then **Deployments** → latest → **Redeploy**. Vite bakes `VITE_*` values in at build time, so changing the variable without redeploying does nothing.

## 7. Keep the backend awake (recommended)

A free Render service sleeps after 15 minutes without HTTP traffic. While it sleeps, scheduled emails don't go out. When it wakes, the worker sends every overdue email immediately, exactly once, but late. The first request after a sleep also takes up to a minute. The login page pings the API on load to start waking it early.

To keep it awake, create a free monitor at [cron-job.org](https://cron-job.org) or [UptimeRobot](https://uptimerobot.com) that requests
`https://email-scheduler-api.onrender.com/api/health` every 10 minutes. One always-on service uses about 744 of the 750 free instance hours per month.

## 8. Check it end to end

1. Open your Vercel URL in a private window and sign in with a Google account that is **not** your own test user.
2. Compose with `samples/recipients.csv`, start time 1 minute ahead.
3. Rows move from *Scheduled* to *Sent*; **View** opens the email on Ethereal.
4. Render → service → **Logs** shows `[worker] listening on queue "email-send"` and one `sent` line per email.

## Notes for a public demo

- **No real email is ever delivered.** Senders are Ethereal test accounts: Ethereal accepts the SMTP message and shows it at a preview link, but never forwards it. Visitors can't use your demo to spam anyone.
- **Every visitor sees the same senders.** Each visitor only sees their own campaigns, emails and search results.
- **Data in Redis isn't persisted on the free Key Value plan.** That's fine: Postgres is the source of truth, and the reconciler re-adds a job for every pending email whenever the service starts.

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `ERR_NGROK_3200 ... is offline` | Vercel still points at ngrok. Set `VITE_API_URL` (step 6) and **redeploy**. |
| Google: "Access blocked: app has not completed the Google verification process" / "only test users" | The app is still in *Testing*. Publish it (step 4.2). |
| Google: `Error 400: redirect_uri_mismatch` | `GOOGLE_CALLBACK_URL` on Render and the redirect URI in Google Cloud must match exactly (https, no trailing slash). |
| After Google you land on the login page with "That sign-in link expired" | You started login on one API URL and came back on another. Make sure `VITE_API_URL` and `GOOGLE_CALLBACK_URL` use the same host. |
| Dashboard says "Cannot reach the server" | The API is waking up (wait a minute), or `FRONTEND_URL` on Render doesn't exactly match your Vercel URL (CORS). |
| Render deploy fails with `Invalid environment configuration` | The log lists each bad variable. |
| Render deploy hangs at migrations | `DATABASE_URL` is Neon's pooled (`-pooler`) URL. Use the direct one (step 1). |
| Compose shows no senders | Step 2 wasn't run against Neon. |
